## 1. Architecture & Security Overview

The Qveto Platform REST API is a multi-tenant backend built with Express, TypeScript, and PostgreSQL (Prisma ORM). All resources belong to an Organization (Tenant), and every request is verified server-side against the authenticated user's organization membership and role.

Client applications must never pass an unverified `orgId` expecting authorization. Tenant scoping is strictly enforced through route parameters and database relationships.

---

## 2. Authentication & Session Management

Authentication uses server-managed sessions stored in the PostgreSQL `sessions` table.

- **Cookie Name:** `sessionId`
- **Cookie Security Attributes:**
  - `HttpOnly`: `true` (Tokens cannot be accessed by client-side JavaScript or XSS attacks)
  - `SameSite`: `Lax` (Protects against CSRF attacks across origins)
  - `Secure`: `true` in production (`https://`), `false` in local development (`http://`)
  - `Path`: `/`
  - `Max-Age`: 7 days (`604,800,000` ms)
- **Bearer Token Fallback:** For mobile or programmatic API consumers, the API also accepts:
  ```http
  Authorization: Bearer <sessionId>
  ```
- **Session Cleanup:** Expired sessions are automatically rejected with `401 UNAUTHORIZED` and cleaned up asynchronously.

## 3. Standard Request & Response Contracts

### 3.1 Request Headers
| Header | Description | Required |
|---|---|---|
| `Content-Type` | `application/json` | Required for POST/PUT/PATCH |
| `Cookie` | `sessionId=<id>` | Required for protected endpoints |
| `X-Request-ID` | Unique tracing UUID | Optional (Generated by server if missing) |

### 3.2 Standard Error Response Shape
All errors return consistent, predictable JSON. Stack traces and database internals are never leaked to clients.

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Invalid request data",
    "details": [
      {
        "field": "email",
        "message": "Invalid email address"
      }
    ],
    "requestId": "48cc5f5b-3790-43a2-9487-86bd6d2f7818"
  }
}
```

#### Common Error Codes
| HTTP Status | Error Code | Description |
|---|---|---|
| `400` | `BAD_REQUEST` / `VALIDATION_ERROR` | Schema validation error or invalid operation |
| `401` | `UNAUTHORIZED` / `INVALID_CREDENTIALS` | Missing session, expired session, or bad credentials |
| `403` | `FORBIDDEN` | Insufficient role or cross-organization denial |
| `404` | `NOT_FOUND` | Resource does not exist or route unmatched |
| `409` | `CONFLICT` | Unique constraint violation (e.g. duplicate email) |
| `500` | `INTERNAL_ERROR` | Unexpected server failure |

### 3.3 Standard Pagination Shape
```json
{
  "data": [],
  "meta": {
    "total": 100,
    "page": 1,
    "pageSize": 20,
    "totalPages": 5
  }
}
```

## 4. Shared Enums & Constants

All enums are defined in `@qveto/shared` and mirrored in Prisma schema.

### 4.1 Organization Roles (`OrgRole`)
| Role | Description |
|---|---|
| `OWNER` | Full administrative control over organization settings, workspaces, and member roles |
| `MANAGER` | Manages workspaces, teams, projects, and task assignments; cannot mutate org settings |
| `EMPLOYEE` | Standard member; accesses assigned resources, updates tasks, and collaborates |

### 4.2 Task Statuses (`TaskStatus`)
- `TODO`: Work backlog
- `IN_PROGRESS`: Actively being worked on
- `IN_REVIEW`: Awaiting review / PR verification
- `DONE`: Completed

### 4.3 Task Priorities (`TaskPriority`)
- `LOW`: Routine, non-blocking
- `MEDIUM`: Standard sprint priority
- `HIGH`: Urgent blocker or sprint priority
- `URGENT`: Critical path / immediate resolution needed

### 4.4 Canonical Task Activity Event Types (`TaskActivityType`)
Defined in `@qveto/shared` and recorded in PostgreSQL `activity_events` table:
- `TASK_CREATED`: Emitted when a new task is created under a project
- `TASK_UPDATED`: Emitted on general property changes (title, description, priority, etc.)
- `TASK_STATUS_CHANGED`: Emitted on status transitions (e.g. `TODO` -> `IN_PROGRESS`, `IN_REVIEW` -> `DONE`)
- `TASK_ASSIGNED`: Emitted when assignee is assigned, reassigned, or unassigned
- `TASK_DUE_DATE_CHANGED`: Emitted when task due date is scheduled, updated, or cleared
- `TASK_ARCHIVED`: Emitted when a task is soft-archived

### 6.4 Workspaces (PRD 02)

All workspace operations require an authenticated user. Workspace access is inherited from verified organization membership; workspace IDs and client-supplied organization IDs are never authorization evidence.

#### `GET /api/organizations/:orgId/workspaces`
Lists workspaces in the verified organization. Defaults to active workspaces only and uses the standard `{ data, meta }` pagination envelope.
- **Auth:** Required; any organization member may list active workspaces.
- **Query:** `page` (default `1`), `pageSize` (default `20`, maximum `100`), `includeArchived` (default `false`). `includeArchived=true` is restricted to `OWNER` and `MANAGER`.
- **Response (200 OK):** `{ "data": [Workspace], "meta": { "total": 0, "page": 1, "pageSize": 20, "totalPages": 0 } }`

#### `POST /api/organizations/:orgId/workspaces`
Creates a workspace in the verified organization.
- **Auth:** Required (`OWNER` or `MANAGER`).
- **Body:** `name` (required, trimmed, non-empty, maximum 100 characters), `description` (optional, nullable, maximum 500 characters). Slugs are server-generated and cannot be supplied by clients.
- Names are unique per organization after trimming and case-insensitive comparison. Names and slugs remain reserved while archived. Slugs are normalized from the initial name and remain stable if the workspace is renamed. Generated collisions receive deterministic numeric suffixes.
- **Response (201 Created):** `{ "workspace": Workspace }`

#### `GET /api/workspaces/:workspaceId`
Retrieves one active workspace. Archived workspace details are visible only to `OWNER` and `MANAGER`.
- **Auth:** Required; membership in the workspace's organization is verified server-side.
- **Response (200 OK):** `{ "workspace": Workspace }`

#### `PATCH /api/workspaces/:workspaceId`
Updates a workspace name and/or description. An empty body is invalid; slug and organization are immutable through this endpoint.
- **Auth:** Required (`OWNER` or `MANAGER` in the workspace's organization).
- **Response (200 OK):** `{ "workspace": Workspace }`

#### `POST /api/workspaces/:workspaceId/archive`
Soft-archives a workspace by setting `archivedAt` to the server timestamp. Teams, projects, and history are preserved. Archived workspaces cannot receive new teams or projects.
- **Auth:** Required (`OWNER` or `MANAGER` in the workspace's organization).
- **Response (200 OK):** `{ "workspace": Workspace }`

#### `POST /api/workspaces/:workspaceId/restore`
Restores an archived workspace without changing its slug. A uniqueness conflict returns `409 CONFLICT`; the server never silently renames or overwrites a workspace.
- **Auth:** Required (`OWNER` or `MANAGER` in the workspace's organization).
- **Response (200 OK):** `{ "workspace": Workspace }`

`Workspace` contains `id`, `name`, `slug`, nullable `description`, `orgId`, nullable `archivedAt`, `createdAt`, and `updatedAt`. Invalid request data returns `400 VALIDATION_ERROR`; missing resources return `404 NOT_FOUND`; cross-organization access or insufficient role returns `403 FORBIDDEN`; duplicate names/slugs return `409 CONFLICT`.

### 6.5 Teams (PRD 02)

Team operations are scoped through their workspace and its organization. Owners and Managers can manage teams and rosters. Employees can list and view only teams where they are a member. Team membership does not replace organization membership.

#### `GET /api/workspaces/:workspaceId/teams`
Lists teams in the workspace. Owners and Managers see all teams; Employees see teams they belong to.
- **Auth:** Required; workspace organization membership is verified server-side.
- **Response (200 OK):** `{ "teams": [Team] }`

#### `POST /api/workspaces/:workspaceId/teams`
Creates a team in an active workspace.
- **Auth:** Required (`OWNER` or `MANAGER` in the workspace organization).
- **Body:** `name` (required, trimmed, non-empty, maximum 100 characters), `description` (optional, nullable, maximum 500 characters).
- Archived workspaces cannot receive teams.
- **Response (201 Created):** `{ "team": Team }`

#### `GET /api/teams/:teamId`
Returns a team and its roster. Employees must be team members; Owners and Managers can view all teams in their organization.
- **Auth:** Required; the team workspace organization is resolved server-side.
- **Response (200 OK):** `{ "team": Team }`

#### `PATCH /api/teams/:teamId`
Updates a team's name and/or description; empty bodies are invalid.
- **Auth:** Required (`OWNER` or `MANAGER`).
- **Response (200 OK):** `{ "team": Team }`

#### `POST /api/teams/:teamId/members`
Adds an organization member to a team's roster.
- **Auth:** Required (`OWNER` or `MANAGER`).
- **Body:** `{ "userId": string }`; the user must be a member of the team's organization.
- **Response (201 Created):** `{ "team": Team }`

#### `DELETE /api/teams/:teamId/members/:userId`
Removes an existing team membership.
- **Auth:** Required (`OWNER` or `MANAGER`).
- **Response (200 OK):** `{ "team": Team }`

`Team` contains `id`, `name`, nullable `description`, `workspaceId`, `createdAt`, `updatedAt`, and `members`; each member includes a safe user summary (`id`, `name`, `email`), `role`, and `joinedAt`. Invalid request data returns `400 VALIDATION_ERROR`; cross-organization access or insufficient role returns `403 FORBIDDEN`; missing records return `404 NOT_FOUND`; duplicate membership or team creation in an archived workspace returns `409 CONFLICT`.

### 6.6 Projects (PRD 02)

Projects belong to a workspace, and their organization is resolved through that workspace. Never trust client-supplied `orgId` or `workspaceId` outside the route. Every operation requires organization membership; project-scoped access also requires project membership unless the caller is an organization `OWNER` or `MANAGER`. An organization `OWNER`/`MANAGER` or the project `OWNER` may manage project settings and membership. Project creation is restricted to organization `OWNER`/`MANAGER`.

New projects require `ownerId` for an existing member of the workspace organization. Creation transactionally stores the project and a matching `ProjectMember` with role `OWNER`. Changing the owner transactionally keeps the owner membership in sync. Existing ownerless projects remain readable and are never assigned an owner automatically; any later owner assignment is explicit.

The accepted statuses are `PLANNING`, `ACTIVE`, `ON_HOLD`, `COMPLETED`, and `ARCHIVED`. Create/update requests may set the first four; archive and restore use dedicated operations. Legacy status strings are preserved and returned until explicitly reconciled. Dates are optional; when both `startDate` and `dueDate` are supplied, `startDate` must be on or before `dueDate`.

#### `GET /api/workspaces/:workspaceId/projects`
Lists projects in an active workspace, using `{ data, meta }` pagination. Organization `OWNER`/`MANAGER` roles see all projects in the workspace; other users see only projects where they are project members.
- **Auth:** Required; workspace organization membership is verified server-side.
- **Query:** `page` (default `1`), `pageSize` (default `20`, maximum `100`), `includeArchived` (default `false`). Archived projects are excluded unless explicitly requested; membership visibility remains enforced.
- **Response (200 OK):** `{ "data": [Project], "meta": { "total": 0, "page": 1, "pageSize": 20, "totalPages": 0 } }`

#### `POST /api/workspaces/:workspaceId/projects`
Creates a project in an active workspace.
- **Auth:** Required (`OWNER` or `MANAGER` in the workspace organization).
- **Body:** `name` (required, trimmed, maximum 100 characters), `ownerId` (required organization member), `description` (optional, nullable, maximum 500 characters), `status` (optional; defaults to `ACTIVE`), optional nullable `startDate` and `dueDate`. The workspace and organization are taken from the route and server-side relationships.
- **Response (201 Created):** `{ "project": Project }`
- Archived workspaces cannot receive projects.

#### `GET /api/projects/:projectId`
Returns an authorized project, including archived projects and legacy ownerless projects.
- **Auth:** Required; caller must be an organization member and either a project member or organization `OWNER`/`MANAGER`.
- **Response (200 OK):** `{ "project": Project }`

#### `PATCH /api/projects/:projectId`
Updates project name, description, status, owner, or dates. Empty bodies are invalid. `ARCHIVED` cannot be set here; restore is explicit. Owner changes verify organization membership and synchronize the `OWNER` project membership in one transaction.
- **Auth:** Required (organization `OWNER`/`MANAGER` or current project `OWNER`).
- **Response (200 OK):** `{ "project": Project }`
- Archived projects reject settings and membership changes with `409 CONFLICT`.

#### `POST /api/projects/:projectId/archive` and `POST /api/projects/:projectId/restore`
Archive sets `status` to `ARCHIVED` without deleting project, task, or membership history. Restore is explicit and uses `ACTIVE` as the restore status because the current schema does not retain the previous status.
- **Auth:** Required (organization `OWNER`/`MANAGER` or current project `OWNER`).
- **Response (200 OK):** `{ "project": Project }`

#### `GET /api/projects/:projectId/members`, `POST /api/projects/:projectId/members`, and `DELETE /api/projects/:projectId/members/:userId`
Lists the roster, adds an organization member, or removes a non-owner membership. A project owner cannot be removed without first transferring ownership; the owner always has a `ProjectMember` record with role `OWNER`.
- **Auth:** Reads require organization and project access; changes require organization `OWNER`/`MANAGER` or current project `OWNER`.
- **Add body:** `{ "userId": string }`; the user must belong to the project organization.
- **Responses:** `GET` returns `{ "members": [ProjectMember] }`; add/remove return `{ "project": Project }`.

`Project` contains `id`, `name`, nullable `description`, `status`, nullable `startDate`/`dueDate`, nullable `ownerId` for legacy rows, `workspaceId`, `createdAt`, and `updatedAt`. `ProjectMember` contains `id`, `userId`, `projectId`, `role`, `joinedAt`, and a safe user summary (`id`, `name`, `email`). Invalid data returns `400 VALIDATION_ERROR`; missing records return `404 NOT_FOUND`; cross-organization or unauthorized access returns `403 FORBIDDEN`; archived-project mutation and duplicate membership return `409 CONFLICT`.

### 6.7 Tasks & Lifecycle Management (PRD 03 Contract)

> **Notice for Developers:** This section defines the agreed contract for the PRD 03 Task module. The Prisma models, safe migration, shared Zod schemas (`@qveto/shared`), and Activity Event contracts are active in the foundation. Route handlers are reserved for PRD 03 implementation.

All task operations are strictly tenant-scoped through `Project -> Workspace -> Organization`. Never trust client-provided `orgId`.

When a project has `status = ARCHIVED`, organization members who are also project members may continue using the existing task, label, and Kanban read endpoints, subject to their established filters. Task creation, updates, task archiving, subtask creation, project-label creation, task-label assignment/removal, and Kanban moves return `409 CONFLICT`. Project archive/restore is an explicit Project Management operation; callers cannot restore a project by patching its status.

#### `GET /api/projects/:projectId/tasks`
Lists tasks for an active project. Normal active task queries exclude soft-archived tasks by default (`archivedAt: null`).
- **Auth:** Required (User must belong to the organization owning the project)
- **Query Parameters:**
  | Parameter | Type | Default | Description |
  |---|---|---|---|
  | `includeArchived` | `boolean` | `false` | When `false`, returns only active tasks (`archivedAt IS NULL`). When `true`, includes soft-archived tasks. |
  | `status` | `TaskStatus` | — | Filter by status (`TODO`, `IN_PROGRESS`, `IN_REVIEW`, `DONE`) |
  | `priority` | `TaskPriority` | — | Filter by priority (`LOW`, `MEDIUM`, `HIGH`, `URGENT`) |
  | `assigneeId` | `string` | — | Filter by assigned user ID |
  | `page` | `number` | `1` | Pagination page number |
  | `pageSize` | `number` | `20` | Items per page (max 100) |
- **Response (200 OK):**
  ```json
  {
    "data": [
      {
        "id": "tsk_cuid123",
        "title": "Build Kanban Drag-and-Drop",
        "description": "Sprint 3 workflow optimization",
        "status": "IN_PROGRESS",
        "priority": "HIGH",
        "startDate": "2026-10-15T09:00:00.000Z",
        "dueDate": "2026-10-22T18:00:00.000Z",

        "createdAt": "2026-10-15T09:00:00.000Z",
        "updatedAt": "2026-10-15T11:30:00.000Z"
      }
    ],
    "meta": {
      "total": 42,
      "page": 1,
      "pageSize": 20,
      "totalPages": 3
    }
  }
  ```

Creates a new task under the specified project.
- **Auth:** Required (Organization member with permissions in project)
- **Validation Rules:**
  - `title`: Required, 1 to 255 characters.
  - `startDate` & `dueDate`: If both are supplied, `startDate <= dueDate` is validated. Rejection code: `400 VALIDATION_ERROR`.
  - `completedAt` & `archivedAt`: Cannot be set by client. `archivedAt` is initialized to `null`. If created directly with status `DONE`, `completedAt` is set to current server timestamp.
- **Body:**
  ```json
  {
    "title": "Design Database Performance Indexing",
    "description": "Composite indexes on (projectId, archivedAt) and completedAt",
    "status": "TODO",
    "priority": "HIGH",
    "startDate": "2026-10-16T09:00:00.000Z",
    "dueDate": "2026-10-20T18:00:00.000Z",
    "assigneeId": "usr_cuid789"
  }
  ```
- **Response (201 Created):**
  ```json
  {
    "task": {
  ```

#### `PATCH /api/tasks/:taskId`
Updates task fields and manages lifecycle state transitions.
- **Auth:** Required (Member of project organization)
- **Lifecycle Semantics (Server-Managed):**
  - **Transition to `DONE`:** When status transitions from a non-DONE state to `DONE`, server automatically sets `completedAt = new Date()`.
  - **Transition away from `DONE`:** When status changes from `DONE` to `TODO`, `IN_PROGRESS`, or `IN_REVIEW`, server automatically resets `completedAt = null`.
  - **Retaining `DONE`:** If a task is already `DONE` and an unrelated field is modified (e.g. title, priority), the existing `completedAt` timestamp is strictly preserved.
  - **Client-Controlled Field Protection:** Clients cannot pass `completedAt` or `archivedAt` in request body.
  - **Date Validation:** If both `startDate` and `dueDate` are present, `startDate <= dueDate` is enforced.
- **Body:**
  ```json
  {
    "status": "DONE",
    "description": "Updated implementation notes"
  }
  ```
- **Response (200 OK):**
  ```json
  {
    "task": {
      "id": "tsk_cuid123",
      "status": "DONE",
      "completedAt": "2026-10-15T15:20:00.000Z",
      "archivedAt": null,
      "updatedAt": "2026-10-15T15:20:00.000Z"

  }
  ```

## 7. Single Activity Event Contract & PRD 04 Integration Guide

### 7.1 Architecture & Storage
All task events reuse the existing PostgreSQL `activity_events` table (Prisma model `ActivityEvent`). No secondary event table or event bus is introduced.

```prisma
model ActivityEvent {
  id         String   @id @default(cuid())
  type       String   // Canonical event types: TASK_CREATED, TASK_UPDATED, etc.
  entityType String   // "TASK"
  entityId   String   // taskId
  actorId    String   // Authenticated user ID who performed the action
  orgId      String   // Server-verified tenant ID
  metadata   Json?    // Structured diff or context
  createdAt  DateTime @default(now())
}
```

### 7.2 Canonical Event Payloads
Every task lifecycle action must generate an `ActivityEvent` with `entityType: "TASK"`, verified `orgId`, and the following metadata convention:

| Event Type | Trigger | Metadata Schema |
|---|---|---|
| `TASK_CREATED` | New task created | `{"title": string, "projectId": string, "status": TaskStatus, "priority": TaskPriority}` |
| `TASK_STATUS_CHANGED` | Task status transition | `{"fromStatus": TaskStatus, "toStatus": TaskStatus}` |
| `TASK_ASSIGNED` | Assignee changed | `{"previousAssigneeId": string \| null, "newAssigneeId": string \| null}` |
| `TASK_DUE_DATE_CHANGED` | Due date modified | `{"previousDueDate": string \| null, "newDueDate": string \| null}` |
| `TASK_ARCHIVED` | Task soft-archived | `{"archivedAt": string}` |
| `TASK_UPDATED` | Other fields changed | `{"changedFields": string[]}` |

### 7.3 Critical Rule: Single Event on Completion
When a task transitions from any status to `DONE`:
- The task service MUST emit **one** `TASK_STATUS_CHANGED` event:
  ```json
  {
    "type": "TASK_STATUS_CHANGED",
    "entityType": "TASK",
    "entityId": "tsk_123",
    "actorId": "usr_456",
    "orgId": "org_789",
    "metadata": {
      "fromStatus": "IN_REVIEW",
      "toStatus": "DONE"
    }
  }
  ```
- **DO NOT** emit duplicate `TASK_COMPLETED` alongside `TASK_STATUS_CHANGED`. The `toStatus: "DONE"` transition is the single canonical representation of completion.

### 7.4 PRD 04 Developer Integration Guide (Notifications & Activity Feed)
The developer implementing notifications and activity feeds (PRD 04) should consume this contract as follows:
1. **Activity History Feeds:** Query `activity_events` filtered by `entityType = "TASK" AND entityId = :taskId` or `orgId = :orgId` ordered by `createdAt DESC`.
2. **Notification Dispatch:**
   - On `TASK_ASSIGNED`: Send in-app notification (`model Notification`) to `newAssigneeId` if `newAssigneeId !== actorId`.
   - On `TASK_STATUS_CHANGED` with `toStatus: "DONE"`: Notify task `creatorId` if `creatorId !== actorId`.
   - On `TASK_DUE_DATE_CHANGED`: Notify task `assigneeId`.
3. **No Redundant Schemas:** Use `@qveto/shared`'s `TaskActivityType` enum to type-check event handling across backend services.
